# Процесс разработки — Olympiad Mentor

Правила для человека и агента при работе с LLM. Цель — снизить риск «LLM написал и сам себе поверил»: явные критерии приёмки (AC), раздельные роли на крупном слайсе, тесты на поведение, базовый quality gate.

Обязательное ядро для агентов — `.cursor/rules/ai-engineering.mdc`. Аудит банка задач — [`ai-workflow/README.md`](ai-workflow/README.md).

---

## 1. Роли: код и проверка — разные модели

| Роль | Где | Что делает |
|------|-----|------------|
| **Implementer** | Cursor (текущая модель чата) | План по AC → код → локальные unit |
| **Verifier** | Другая LLM, не Cursor | Ревью диффа, требований и рисков, поиск дыр и «тесты зеркалят код» |

На крупном слайсе:

- Implementer не объявляет «готово к коммиту», пока не прошёл Verifier (человек передаёт его вывод в чат или резюмирует).
- В чате подписываются модели: `Implementer: <модель в Cursor>`, `Verifier: <модель вне Cursor>`.
- Мелкий hotfix (опечатка, один assert, docs-only) — проверка другой моделью по желанию.

Verifier проверяет:

1. Соответствие AC: входы, выходы, ограничения.
2. Инварианты продукта (§6).
3. Тесты проверяют поведение, а не копируют внутренности.
4. Нет хардкода одного стенда как «истины продукта».
5. Риски регресса как сигнал.

---

## 2. Слайс

До кода крупного слайса Implementer пишет в чат AC и ждёт «ок» / «делай» (кроме аварийного hotfix):

- **Цель** (1–2 предложения)
- **Входы / выходы**
- **Ограничения**
- **Приёмка** (unit + smoke)
- **Out of scope**

Порядок:

1. AC → «ок» / «делай».
2. Код с комментариями (§7).
3. Краткая приёмка человеком / smoke.
4. Unit-тесты отдельным шагом.
5. Ревью тимлида: ✅ / ⚠️ / 🔴.
6. Verifier — на крупном слайсе.
7. Коммит, пуш и мерж — только по команде; необходимая документация обновляется вместе с коммитом, пушем и мержем.

Запрещено в одном промпте без явного разрешения: «сделай фичу и сразу тесты под покрытие».

## 3. Тестирование

### Unit

- Обязательны на поведение затронутого кода.
- Ориентир coverage на `lib/*` — ~85%: это следствие качества тестов, а не цель «добить Miss line».
- **Хороший unit:** вход → ожидаемый выход, ошибка или инвариант (например, подсказка не содержит эталонного ответа).
- **Плохой unit:** assert на приватные флаги реализации один-в-один с ветвлением кода.
- Без live-зависимостей, где возможно (live LLM в unit не вызываем).
- Unit ≠ продуктовая приёмка на живом стенде.

### Ручные и автоматические тест-кейсы

- До стабилизации MVP не пишем.
- SRS не подгоняем под генератор тест-кейсов, но требования держим трассируемыми (ID, входы/выходы).
- После MVP: ручные тест-кейсы → автотесты по ним; при желании — генератор тест-кейсов.
- Из практики других проектов берём только процессные правила, без их стендов и эталонных тест-кейсов.

### Quality gate

| Слой | MVP | После MVP |
|------|-----|-----------|
| Lint / format | желательно | gate в CI |
| Unit ~85% | **обязательно** на код слайса | держать |
| Продуктовый smoke | после крупных волн | да |
| Ручные ТК → авто | нет | да |
| E2E visual / mutation | нет | по необходимости |

---

## 4. Продуктовый smoke

1. После крупной волны — короткий прогон на реально поднятом приложении, не только unit.
2. Если есть отдельные frontend и backend, оба должны быть живы перед ручной UI-проверкой.
3. Проверять health и главный сценарий слайса; фиксировать P0 / P1 / P2 в чат или backlog.
4. Не использовать старые «золотые» ручные тест-кейсы как оракул, пока требования меняются в MVP.
5. Секреты и локальные артефакты прогонов — не в git.
6. Узкий hotfix или docs-only — полный smoke по желанию.
7. Крупная волна без продуктового взгляда человека — не «готово к ежедневному использованию».

## 5. Git

| Правило | Как делаем |
|---------|------------|
| Коммит / пуш / мерж | Только по явной команде: «коммит», «пуш», «мерж» |
| Формат | `feat(scope):` / `fix(scope):` / `test(scope):` / `docs:` / `docs(scope):` / `ci(scope):` / `chore(scope):` / `refactor(scope):`. Subject на русском допустим; body — зачем |
| Scopes | `auth`, `content`, `trainer`, `mentor`, `progress`, `web`, `api` |
| Ветки | От актуального `main`: `feature/…`, `fix/…`, `docs/…` (для волн допустимо `feature/iter-N-…` или `feature/qa-wave-…`) |
| `main` | Работа в feature-ветке; в `main` только через явный «мерж» |
| После merge | Правка затронутых документов (SRS / ARCHITECTURE / USER-GUIDE) в том же PR; `docs/HISTORY.md` — только вехи |
| Не коммитить | `.env`, секреты, `*.db` / `dev.db`, `node_modules/`, локальные артефакты |
| Lockfile | Корневой `package-lock.json` коммитить (один Next/Node-пакет) |

---

## 6. Продуктовые инварианты

- Секреты только в `.env`, не в git.
- LLM API — opt-in; обязателен fallback без LLM (контентные подсказки).
- Наставник не спойлерит эталон без явного запроса или исчерпания политики попыток.
- Ссылки наставника — на внутренние статьи, а не на случайный интернет (если иное не оговорено в AC).

---

## 7. Комментарии в коде

Подробно и на русском: функции, блоки, неочевидные решения — чтобы код мог прочитать не-программист.

---

## 8. Чеклист перед «можно коммит?» (крупный слайс)

- [ ] AC согласованы
- [ ] Код с комментариями на русском
- [ ] Unit отдельно, по поведению, ориентир ~85% на затронутом
- [ ] Smoke локально (если UI/API)
- [ ] Ревью тимлида ✅ / ⚠️ / 🔴
- [ ] Verifier вне Cursor (если крупный слайс)
- [ ] Необходимая документация обновлена в том же коммите
- [ ] Явная команда человека «коммит»
