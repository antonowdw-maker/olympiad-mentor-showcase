# Playbook: роли ревью

> Документ витрины. Полный банк, трекер `content/sources/`, решатели `lib/content/audit/`, отчёты и локальные материалы (`docs/audit/`, `docs/doc/`, `tmp-*`, `docs/REVIEW*`) находятся в приватном репозитории; упоминания этих путей описывают его.

> Справочник ролей для самопроверки Implementer-а перед передачей отчёта
> Verifier-у. LLM **читает** этот файл в начале работы над пакетом,
> выбирает роли по §3, отчитывается в шапке отчёта по §4.
>
> Пользователь может переопределить любой выбор: «добавь [D]», «убери [C]»,
> «проверь ещё [A]». Решение пользователя приоритетно.

## 0. Три класса дефекта «сверка с самим собой» (T8a–T8c)

Самопроверка не считается сверкой с источником, если объект сравнивают
с копией себя. Три повторявшихся класса:

1. **`orig` = `text`** (T8a, T8c). Поле `orig` — та же константа, что
   условие канона. Правило: `orig` — независимый источник (`origFile` +
   `origSha256` файла в `tmp-olymp6/txt/`), либо `orig: null` и пометка
   «оригинал не сверялся».
2. **Ложная атрибуция файла** (T8b). В `sourceHint` / `official` / proofs §0
   указан файл «офиц. решение 6 кл.», а файл — другой класс / номер / задача.
   Правило: любую ссылку открыть и сверить класс, номер, формулировку.
3. **`official` = значение из сида** (T8c). Поле `official` без внешнего
   файла, тест «контроль решателей» круговой. Правило: `official` только из
   открытого файла (`officialFile` + `officialSha256`); иначе `null`, в
   proofs «—», канон не входит в сверку `official`.

**Автотесты.** Структурный (CI, поля `T*_SRC`): `official === null` →
канон пропускается в «контроле решателей»; `official !== null` → обязательны
`officialFile` и `officialSha256`; `orig === null` **или** заполнены
`origFile` и `origSha256`, и они не равны хешу / пути строки `text`.
С T8d: обязательны `risk` (enum) и `searchLog` — см. [C] / [D] и §12.
Локальный `scripts/audit-<тема>-proofs.ts` читает `tmp-olymp6/txt/<origFile>`,
сверяет хеш и текст, падает при расхождении; хеш — в шапке proofs;
печатает `searchLog` в proofs §0.
Истинность подсказок (тип величины: путь / время / вес / деньги) — **ручная
проверка V2-files**; автоматом не ловится.

Слои V1-text / V2-files — **§11**, здесь не дублировать.

## 1. Каталог ролей

### Группа CONTENT — аудит задач и контента
Роли этой группы активны по умолчанию, когда меняется содержимое банка
(`content/seed/**`). Это 90% текущей работы проекта.

#### [A] Численник — только арифметика
**Что смотрит:** только числа. Никакой логики, никакой математики, только
арифметика в отчёте и proofs.
**Что проверяет:**
- суммы по методам (`П + Ф + Р + Т`) = общее число сущностей;
- суммы по §7.3: базовые страты + страта риска без двойного счёта;
- агрегации классов: `A + B1 + B2 + B3 + H + C` = всего правок;
  пересечения (B2 ⊂ B3 или «B3 = 18, из них B2 = 2») пишут явно и не
  суммируют дважды (T1g: иначе 9+3+2+18 = 32 при 30 сущностях);
- составные части в §2 (задач по файлам → задач всего → сущностей);
- примеры в выкладках: `C(n,k)`, `2^n`, факториалы, дроби, корни;
- округления и нецелые числа (если есть нецелое — обосновать или исправить);
  «ближайший момент» — минимум среди **рациональных** решений, не среди
  целых; в выкладке модуль 720: `(4·направление + 720k) : 13` (T8e,
  биссектриса: `216 : 13 ≠ 72`);
- правило «одно число везде»: `T*_CHECKS` = строки `proofs §1` = `it.each`;
- `T*_CHECKS + страховочные тесты` = всего тестов в файле;
- арифметику в подсчётах страты риска;
- сверку номеров сущностей между разделами (§5, §6, §7, §10) с proofs §1 —
  один и тот же номер = одна и та же сущность; состав выборок соответствует
  заголовку (в «выборке П» нет Ф-строк); пересечения классов (одна сущность
  в двух классах) показаны явно и не дают двойного счёта;
- диапазоны номеров («№ X–Y»): если диапазон пропускает отдельные строки —
  пропуск указан явно («№ 1–27, кроме 10»), а не спрятан в перечне;
- счёт «N полей / N строк / N функций» в артефакте сверен с реальным
  фильтром теста или скрипта: если часть данных исключена или обработана
  особо — сказано, как именно («30 полей, даты вырезаются из текста перед
  проверкой»), а не только общее число;
- при переносе задач из старого `t*-checks.ts` в новый пакет: если снято
  записей не 3 × (число задач) — в §3 отчёта сказано, каких сущностей в старом
  файле не было и почему (T9b: снято 23 из 27 — у min-xy × 3 и frame-rect i1
  записей в первом аудите не было); если снято **0** и старый файл не менялся —
  тоже одной строкой в §3 и в §10 [A], почему (T9d: 9 авторских задач в первом
  аудите проверялись вне `t9-checks.ts`);
- **поправка замечания Verifier-а** (T9f, V1 П1): если Implementer нашёл
  арифметическую ошибку в замечании V1 / V2 (в том числе пред-стартовом) и
  не принял её в выкладку, это отдельная строка в §10 [A]: что было в
  замечании, что стоит в выкладке и почему («М · Ы ≤ 81 → ≤ 9 · 8 = 72:
  М и Ы — разные буквы, значит разные цифры»); молча исправлять нельзя;
- перед каждой передачей Verifier-у: статус коммита и SHA в §3
  («Артефакты») совпадают с шапкой отчёта (закоммичено / запушено, какие
  коммиты) — после каждого нового коммита правятся оба места;
- **единицы счёта страты** (T8a, V1): «страта риска» в отчёте и proofs §0.4
  всегда в **канонах** (не в сущностях). Разбивка «× 3 варианта» — только в
  §7.1 и только с явной пометкой «5 канонов (15 сущностей)». Смешивать
  «5 задач × 3 = 15» без слова «канонов» нельзя: сверка с §0.4 ломается;
- **V1-text не пишет «проверено»** для артефактов, видимых только V2-files
  (SVG, сид, решатели, границы перебора, трекер, БД). Формулировка:
  «не проверял — задача V2» (T8a/T8b: иначе V1 закрывал слой, которого
  не видел);
- **непрерывные задачи** (движение, время): эталон — аналитическое решение
  **плюс** независимая численная модель (в т.ч. Python), не только формула.
  Прецедент T8b eight-lap: `tL² : (tL − tS)` без контроля — не доказательство;
- **детектор B3 не игнорирует `%`:** регулярка не должна исключать числа,
  за которыми стоит `%`. Шаблон `(?<![\d/,])${ans}(?![\d/,%])` — ошибка:
  исключение `%` маскирует B3 (T8b, крокодилы i1: ответ 20 в «20% пусты»);
- **параллельные варианты одной конструкции в одном пакете** (T8c): развести
  числа и ответы между семействами (squirrel-week / three-barrels);
- **имя ≠ объект** (T8b, уточнение T8c): правило применимо к **счёту меток**
  ([A] проверяет, что «постановка N + только числа M = числу вариантов»).
  Смена имён, чисел или дат при том же вопросе и тех же объектах — «только
  числа». Объекты — то, о чём задача (ватрушки, муравьи, крокодилы,
  даты-палиндромы). Смена объекта (крокодилы → акулы) или типа вопроса —
  «постановка». Прецедент T8c: 0 + 20 = 20. Сами метки в сиде и отчёте
  ставит **[B]**;
**Формат артефакта:** каждая сумма пересчитана явно — «13 + 6 + 11 = 30 — ✅»;
для сверки номеров — перечислены номера строк, которые сверены.
**Чего НЕ делает:** не проверяет правильность формул, не смотрит на условия
задач, не сверяет с источниками. Только счёт.

#### [B] Редактор-процессник — текст, формулировки, процесс
**Что смотрит:** как текст отчёта и сида читается учеником и пользователем.
**Что проверяет:**
- названия задач и вариантов: числа словами («Трое из пяти» при 6 учениках),
  несоответствие условию, `INSTANCE_TITLE_MISMATCH`;
- ссылки «Та же задача», «В каноне», «Как в примере», «Как в марсианском
  светофоре» — должны быть либо раскрыты, либо отсутствовать;
- подсказки, называющие ответ (класс H): прогон по всем сущностям,
  поиск главного эталона отдельным числом / словом; у ответа-списка — каждого
  элемента. **Оценка тоже считается** (T9e, V1 К1): если подсказка
  содержит число из итогового ответа хотя бы как оценку сверху / снизу
  («ОН не больше 12» при ответе «0, 12, 96»), это класс H, даже если оценка
  взята из официального решения. Подсказку переписывают вопросом («Сколько
  может быть самое большое ОН?»).   Ложные срабатывания поиска (число из
  условия, перечень данных, docSlug) разбираются по категориям в §8 отчёта;
- **истинность утверждений в подсказке** (T9f, V2): каждое фактическое
  утверждение (разряд буквы, оценка, название величины) проверяется
  подстановкой параметров **этой** сущности; ложь вроде «Е стоит в сотнях у
  обоих слагаемых» при ЛЕТО + ЛЕС — дефект, даже если число ответа в
  подсказке не названо. Артефакт — список ложных утверждений. **Это не
  класс H и не роль [H]:** класс H — утечка ответа (поиск числа / слова
  эталона); истинность — факт-чек текста подсказки (роли [B] и [C]). Две
  проверки, две пометки; сводить в одну нельзя (иначе ложь снова
  проскочит, как в T9f до фикс-пакета);
- вырожденные варианты (класс B3): пересказ условия, ответ прямо в условии,
  ссылка на канон, сведение к вспомогательному шагу решения; вариант
  не считается самостоятельным и тогда, когда ответ виден из **одного**
  отличающегося слагаемого / числа / столбца без применения идеи канона
  (T4c4, 2.9.1 i1: две «лесенки» совпадали во всех разрядах, кроме
  единиц, — заменён вариантом, где различаются несколько разрядов и
  младший «тянет» в другую сторону). Класс правок H (подсказка называет
  ответ) и роль [H] Prompt Injection — разные вещи: в отчёте класс пишется
  без скобок, роль — в квадратных скобках; в метках «постановка / только
  числа» H-вариант считается отдельно («только числа — 8 + H 1»);
- **B3 > 15 — сигнал владельцу** (T9f, V1 К1): если в пакете заменено больше
  15 вырожденных вариантов, в шапке отчёта («Итог пакета») и в §5.3 пишется
  дословно «B3 = X > 15 — сигнал владельцу» и причина («все N старых
  вариантов вырождены — подсчёт букв, число из условия канона; замена
  полная»).   Сигнал без причины не засчитывается; при B3 ⩽ 15 — строка
  «B3 = X ⩽ 15 — сигнала нет»;
- **счёт B3 при классе R** (T9f, V2): в порог 15 входят только **живые**
  исправленные варианты сохранённых задач. Удалённые сущности заменённой
  задачи в B3 не входят; новые варианты замены считаются отдельно
  («исправлено B3 = 18; R — 1 канон + 2 новых варианта»). Формула
  «V + R + B3 = 30», где B3 включает удалённых, вводит в заблуждение;
- `findVariantCollisions`: одинаковые условия, одинаковые наборы ответов
  **внутри одной задачи** (канон и её варианты). Совпадения ответов между
  разными задачами пакета («да» / «нет» / «6») в проверку не входят;
  в proofs §3 писать «внутри каждой задачи», иначе «0 / 0» читается как
  «во всём пакете нет одинаковых ответов» (T9f, V2);
  сравнение — **только текст** (без title и SVG). Если i1/i2 совпадают
  по словам, а числа на рисунке разные — в proofs §3 писать «текст один,
  рисунки различны (клетки …)», не считать дублем; в отчёте §5.2 явно,
  если различие только в фигуре (T8e, рыбки, V1/V2);
- **идентичные ответы в семействе — блокер; исключений нет** (T8d, weather;
  прецедент T8c squirrel i2 = канон). Если структура вопроса (двоичный ответ
  «пасмурная / солнечная») при любом корректном наборе чисел даёт одно и то
  же слово, **меняют постановку варианта** (другой вопрос: «сколько задач
  в последний / предпоследний день»), а не пишут «так устроена задача».
  Исключение — только явное решение владельца в шапке отчёта;
- класс C: если слаги `i1`/`i2` не менялись — написать явно «C — нет»;
- расхождения отчёт ↔ proofs (что-то есть в отчёте, нет в proofs — и наоборот);
- при переаудите у темы два proofs-файла — старый (история первого аудита) и
  новый пакета; §2 «старые формулировки» **каждого** из них начинается с
  пометки, какое состояние он хранит (до какого PR / SHA), и указателя на
  второй файл (T9a: V1 сверил отчёт §5 с историческим §2 `t9-proofs.md` вместо
  `t9a-proofs.md` и выставил ложный блокер); отчёт сверяется только с proofs
  своего пакета;
- если в §10 отчёта что-то закрыто, а в тексте это не отражено — дефект;
- выкладки proofs §1 читаются без текста условия: если число из условия —
  не прямое произведение / сумма видимых параметров (строка цифр,
  разбитая на числа; ошибочная запись в условии), выкладка **словами**
  описывает, что перебирается, и только потом даёт результат («отметки
  выписаны подряд, строку режут знаками умножения на числа, их
  произведение — 2007; … строка 33223 разбивается как 3 · 3 · 223»); без
  сжатых значков (`|`, отсортированные цифры в скобках, «=» между строкой
  и произведением); если нет — кандидат на правку генератора proofs.
  Уравнение вида `T − T/k = Δ` выписывают явно, без «обычное T из …»
  (T8d ivan: `T : 1,6 = T − 65; T = 520 : 3`). Включение-исключение —
  числовыми слагаемыми, не «минус пары плюс тройка» (T8d dishes:
  `121 + 91 + 73 − 30 − 24 − 18 + 6 = 219`). Если строка формата добавляет
  ограничение, которого нет в источнике — в `T*_SRC[slug].note` явно, что
  добавлено и почему (T8d five-sums). `risk` ради поиска допустим, если
  в `note`: «повышен намеренно…; перебор единствен»;
- нестандартная структура задачи (строку режут на числа, число из
  условия ≠ произведению / сумме видимых параметров, в условии
  заведомо ошибочная запись): текст задачи сверяется с источником
  **до** формулировки выкладки — ошибка чтения условия даёт неверную
  выкладку (T4b2: «отметки по возрастанию» вместо «в порядке записи»);
- **небинарный вариант у да/нет-канона:** хотя бы один i1/i2 с ответом
  не «да/нет» (число, имя, список). Счёт — по канонам, проверка по
  `acceptedAnswers` в proofs §0.1, не по списку номеров (T1g: #66 оба
  бинарные не входят в счёт, пока i2 не стал числом ходов);
- новые варианты (B3): у каждого явно отмечено, что он меняет — **постановку**
  (другой вопрос, другой приём решения) или **только числа** при той же
  постановке; в отчёте — пометка у каждого варианта, а не общее заявление
  «варианты меняют постановку» (T4b3: 6 из 12 меняли только числа).
  Метка ставится **относительно канона**, а не соседнего варианта: изменился
  тип вопроса («существует ли» → «наименьшее», «пример» → «сколько»), объекты
  или приём — «постановка», даже если числа тоже другие; тот же вопрос и те
  же объекты с другими значениями — «только числа» (T4c3, 2.4.8: i1 и i2 оба
  спрашивают «наименьшее x» при каноне «существует ли» — оба «постановка»).
  Ребусы (T9c, ust02 i1): тот же набор букв, то же действие, то же число
  разрядов и тот же вопрос, а меняется только расстановка букв в одном слове
  (ТИК + ТАК = АКТ → ТИК + ТАК = АКИ, в обоих «все значения суммы») —
  «только числа»; изменился набор букв, действие, число разрядов или вопрос
  («все значения суммы» → «сколько различных букв») — «постановка».
  Индекс в вопросе (T9d, system-xy i1: «за третью книгу» → «за вторую»):
  если меняется только номер k при той же формулировке («сколько за k-ю
  книгу», «на k-й картинке», «в k-м кошельке») — «только числа»; если
  меняется сама формулировка («сколько за k-ю» → «сколько за все»,
  «сколько на k-й» → «на какой картинке») — «постановка».
  Дополнительно (T9f, V2): вариант **вырожден относительно соседнего
  варианта**, если его ответ получается подстановкой из готового решения
  соседа без новой идеи (tigr: «наибольший ТИГР» и «наибольший СПИТ» —
  один кластер 3941 + 3952 = 7893). И вырожден относительно канона, если
  спрашивает **побочный результат того же решения** (eh-moroz: Э + Х = 13
  сразу из канона 72 = 36 + 36). Такие варианты заменяют или явно помечают
  в отчёте;   сравнение только «вариант vs канон по метке постановка / только
  числа» этого не ловит.
  При замене вырожденного варианта в паре `i1`/`i2` проверяют, не стал ли
  новый вариант вырожденным **относительно своего нового соседа**: ответ
  не должен читаться из готового решения соседа без новой идеи. Совпадение
  схемы (тот же набор и те же стойки, вопросы «существует?» / «чему равна
  короткая») — повод заменить один из двух (T1h #79);
- **мёртвые подсказки** (T8b Пончик, T8c Амир/Фома): «Подбери целое d»,
  «Посчитай» без шага — дефект. Заменить на конкретное действие;
- **подсказка-вычисление** (T8c купцы i2) — обратный дефект: «сложи два
  числа и возьми половину» = арифметика ответа. Подсказка даёт **шаг
  рассуждения**, не готовый счёт;
- **независимость варианта от варианта** (T8c date i2): вариант не опирается
  на данные, которые даёт решение соседнего варианта (старт i2 ≠ ответ i1);
- **метки «постановка / только числа»** — редактор ставит по правилу
  «имя ≠ объект» ([A] выше): смена чисел / имён / дат при том же вопросе и
  объектах — «только числа». [A] только пересчитывает сумму меток;
- **словесные пары и время:** принимать «a и b», «a, b», «a,b»; для времени —
  с «ч», «:00», «.00»; для дат — цифровые формы и словесную. Отрицательный
  контроль — перестановка («1 и 10» при эталоне «10 и 1»);
- **согласование имён** (T8b, 3.5): шаблон «Братья X и Y» — оба имени
  мужские. Иначе переформулировать («Брат и сестра») и согласовать
  местоимения / «идёт в …»;
- **класс R → варианты с нуля** (T8b, восьмёрка): после замены канона
  i1/i2 пишутся заново. Нельзя переносить канонный SVG и старую постановку
  с новыми числами;
- **эталон варианта верен для текста варианта** (T8b, 3.3, Пончик):
  если вариант написан нами, пропуск математически допустимых ответов
  нельзя списать на «как у организаторов». У организаторов это решение
  владельца **только для канона**;
- **календарные даты и високосный год** (T8a, V2): если в условии две даты
  одного года **без года**, число суток между ними должно совпадать при 28
  и 29 днях февраля (артефакт — таблица «даты → сутки невисокосный /
  високосный»). Иначе вариант зависит от високосности (T8a squirrel i1:
  20 февраля → 10 марта = 18 суток в 2019 и 19 в 2024). Правка: даты вне
  февраля или интервал, не пересекающий 29 февраля; эталон и `T*_CHECKS`
  пересчитать;
- формат ответа в задачах на сравнение **следует формулировке вопроса**
  (решение владельца 2026-09-29, T4c4): «Сравните …» — знак >, < или =
  между первым и вторым (строка «Ответ: знак >, < или = между первым и
  вторым числом.»); «Что больше …» / «Какая из них больше (или они равны)» —
  слово из вопроса («первая» / «вторая» / «равны», «нечетных» / «четных» /
  «равны»), и эти слова перечислены в строке формата. Синонимы в
  `acceptedAnswers` — только естественные («равны», «они равны», «суммы
  равны»; «е» и «ё»); знак к словесному ответу и слово к знаку не
  добавляются. Слово-ответ не должно встречаться в подсказках (валидатор
  `HINT_LEAK` ловит «нечётных» в «Сколько нечётных чисел…») — проверка:
  главный ответ каждой сущности стоит в её строке формата (тест T4c4);
- оговорка, которой нет в тексте источника, но без которой официальный ответ
  не единственный (T9b, guards МП 1994: «в бригаде больше одного сторожа», иначе
  подходят ещё три тройки с g = 1): её ставят в скобки строки формата, только
  если это **ограничение постановки** (натуральное прочтение текста, его молча
  использует официальное решение), а не новое правило задачи; в proofs §0 / §0.1
  и   в §8 отчёта — пометка «ограничение постановки из официального решения, не
  из текста источника», а не «формат ответа»;
- **«найдите все решения» — список по возрастанию** (решение владельца
  2026-10-03, T9f, ЛЕТО + ЛЕС = 2011): если источник просит все решения, а
  каждое решение задаётся одним числом (значение слова, номер, количество),
  строка формата просит «все значения … в порядке возрастания через запятую»;
  в `acceptedAnswers` — слитная форма «a,b,c» и официальная запись ответа
  дословно (равенства, обратный порядок, если так у организаторов);
  неполный и лишний список, другой порядок (кроме официального) и одно
  решение не принимаются (отрицательный контроль). Это не класс B: вопрос
  источника не меняется;
- **ответы «да / нет»** (T9f): «да» обосновывается конструкцией (пример в
  выкладке proofs), «нет» — инвариантом или оценкой; формы в `acceptedAnswers`:
  «да» / «нет», с глаголом из вопроса («да, можно», «нет, не может») и один
  глагол; у «можно» отрицание — «нельзя», не «не можно»; отрицательный
  контроль — противоположный ответ и противоположный глагол;
**Формат артефакта:** каждое найденное место — с номером сущности
и кратким диагнозом.
**Чего НЕ делает:** не считает числа, не проверяет математику, не открывает
источники.

#### [C] Факт-чекер — связь с внешними источниками
**Что смотрит:** связь задач с источниками. Порядок поиска условий и офиц.
решений без пропуска шагов — `project-context.mdc` и
локальной описи §3 (не копировать полный реестр сюда).
**Порядок поиска источника (T8d+, поле `risk`; локально 1–2; шаг 3 — Implementer сам):**
1. Локально: `docs/doc/materiali/` — по описи локальной описи §3. Обязательно просматривать: `решения математика/**` (включая `math510keys`, `math510stage1keys` и копии «(1)»); три zip в `docs/doc/` (ключи ПВГ и др.); `математика доп/` (листки, в том числе не вошедшие в `tmp-olymp6`).
2. Локально: `tmp-olymp6/` — `txt/`, `pdf/`, `index.txt` (фрагмент условия). **`answers-map.txt` не доказательство отсутствия ответа:** на 2026-10-10 в нём «ответы» помечены у 12 листков из 191, но многие листки печатают ответ под задачей. Сначала открыть сам листок. Шаги 1–2 всегда.
3. Сеть (таймаут 30–60 с). **Implementer** выполняет самостоятельно, если шаги 1–2 не дали источник или официальный ответ; при обрыве — не догонять, в `searchLog` статус
   `"найден, не скачан (обрыв)"`. **V2-files (Claude) в сеть без команды владельца не ходит; при необходимости сам задаёт владельцу вопрос в сессии (что открыть и зачем), а не откладывает в отчёт.**
4. Скачивание в `tmp-<пакет>/` делает **Implementer (Grok)**, не V2.
**Классификация источников.** Первоисточник и способ доступа — разные вещи.
**Первоисточник** — откуда задача родом (олимпиада, вступительный тур олимпиадного типа, авторский сборник). В `sourceHint`, `T*_SRC.note` и proofs §0 всегда указывают первоисточник.
**Способ доступа** — как текст и ответ попали к нам (файл или `sourceId`). Способы по реестру [`CONTENT-QUALITY.md`](../CONTENT-QUALITY.md) §2: **A** сборник-агрегатор (S6-A `6math2023.pdf`, S6-B `matholymp67.pdf`); **B** листок олимпиады (`tmp-olymp6/`, `математика доп/`); **C** файл решений (`решения математика/**`, zip ключей); **D** прочие файлы реестра (S6-C…S6-F); **E** сеть (таблица §2.1; домен `mathus.ru` — сюда, не к локальной папке `mathus/`).
6math2023 и matholymp67 — **агрегаторы олимпиадных задач**, не отдельный класс источника: в 6math у каждой задачи указана олимпиада. Позиция в 6math (например §7.3.20) — **указатель для topic-gate и трекера**, не класс источника.
По умолчанию допустимы **олимпиадные** первоисточники (включая вступительные туры олимпиадного типа). Учебники Петерсон / Гейдман / 57-й школы, шпаргалки, научпоп-головоломки, «В помощь родителю» — **не** для замены канонов без решения владельца. Кандидаты на решение владельца — сборник вступительных в матшколы и сборники СПб олимпиады в `docs/doc/materiali/Материалы/`.
**`linear`:** условие не допускает разных прочтений, единственность в
proofs §1 (перебор или уравнение). Движение, сводящееся к линейному
уравнению (`D : 60 = t + 3`), — `linear`, не `continuous`. `continuous` —
геометрия / модель **без** сведения к уравнению (прецедент T8b eight-lap).
`reading` — трактовка **формулировки**; порядок прихода / доли —
`proportion`, не `reading` (прецедент T8c Лего).
**`searchLog`** живёт в `T*_SRC`, не пишется руками в proofs. `url` —
сетевой URL **или** локальный путь (`docs/doc/materiali/…`, `tmp-olymp6/…`).
Если офиц. файл уже найден локально — статус `"найден"` и `file`, **не**
`"не проверялась — линейный канон"` (прецедент: метла, палиндром T8c).
Статус `"не проверялась — линейный канон"` допустим **только** при
`risk = linear`. При `risk !== linear` и `official = null` после шагов 1–2
шаг 3 (сеть) **обязателен для Implementer-а** и выполняется им **без команды
владельца**. **V2-files (Claude) в сеть без команды владельца не ходит; при необходимости сам задаёт владельцу вопрос в сессии (что открыть и зачем), а не откладывает в отчёт.** Допустимые
итоги в `searchLog`: `"найден"` (файл в `tmp-<пакет>/`),
`"найден, не скачан (обрыв)"` (HTTP-код / таймаут),
`"нет на сайте организаторов (HTTP 404)"`. Статус `"не искалось"` при
`risk !== linear` **запрещён**. Если шаг 3 выполнен — в `searchLog` HTTP-код
(404 / 500 / 504), не «решение не публикуется».
Формулировка «решения не публикуются» **запрещена** — только статусы
`searchLog`.
**Класс файла** перед записью `officialFile`: сверить класс, номер, год,
олимпиаду (T8b: файл «Ломоносова» оказался 5 кл., не 6).
**Что проверяет:**
- **три класса «сверка с самим собой»** — §0;
- **истинность утверждений об источнике** (расширение T9f): не только
  подсказки, но и `sourceHint`, `official`, proofs §0;
- **ссылка на файл проверяется отдельно:** открыть файл, сверить класс /
  номер / задачу (T8b: PDF «6 кл.» оказался 5 кл.);
- для каждого канона из источника: есть ли ссылка в `sourceHint` или в
  proofs §0; в proofs §0 явно сказано, найден ли оригинал / офиц. решение на
  шаге 1, 2 или 3;
- ссылка открывается и ведёт на нужный номер задачи;
- если действует правило дословности: текст канона в сиде совпадает с
  источником (или отклонение обосновано);
- если правило дословности применяется к вторичному источнику (сборник,
  например 6math2023), а при расхождении с оригиналом олимпиады берётся текст
  оригинала — явно сказать это во введении отчёта и proofs §0, перечислить
  каноны, где текст сида взят из оригинала, и показать оба текста в proofs
  §0.1 (две колонки); тест `startsWith` сверяет условие именно с выбранным
  текстом (поле вида `SRC[slug].text`), а не со сборником;
- **задачи на построение — три класса** (решение владельца 2026-09-29, T4c2).
  Если в источнике ответ — не число / список / свойство, а выражение или
  конструкция, задачу относят к одному из классов:
  - **A** — обычная задача: ответ — число, список чисел, «да / нет», короткое
    свойство. Берём без ограничений;
  - **B** — конечное множество решений или единственное свойство, и ответ
    можно выразить в текущей механике ввода: число («сколько решений»,
    «наименьшее количество минусов»), список («все решения»), свойство
    («какие суммы возможны»). Берём: условие дословно, вопрос переформулирован
    под допустимую форму ответа (отдельной фразой после текста источника).
    Смысл сохраняется — чтобы ответить, ученик по-прежнему должен найти
    решения, а не угадать; в `sourceHint` — «· дословно, вопрос переформулирован ·».
    **Критерий «единственность» недостаточен** (T9f, ust05): если ответ
    получается оценкой или инвариантом **без построения объекта** и при этом
    легко угадывается (произведение шести букв = 0, потому что 720 > 72),
    это фиксируют в proofs §0.3 явно; вопрос канона можно оставить, если
    построение закрывают варианты. «Ученик по-прежнему ищет решение» писать
    нельзя, если оценка достаточна;
  - **C** — бесконечное множество ответов или нужен свободный ввод выражения /
    конструкции / доказательства. Не берём: в трекере `skip` с заметкой
    «класс C: требует нового класса задач (ответ-выражение)», в §7 отчёта —
    строка бэклога, в счётчик задач трекера не входит.
  Критерий B / C: ответ записывается числом / списком / свойством — B;
  нужен свободный ввод выражения / доказательства / конструкции — C.
  Примеры (6math2023): 2.2.1 лотерея и 2.2.3 «поставьте числа и знаки → 623» —
  C; 2.2.4 «знаки до 2022 с наименьшим числом минусов» — B (ответ 1);
  2.3.1 «найдите три решения МА = Р × К = Е + Р» — B (сколько решений);
  2.3.2 «найдите три решения ∗∗+∗∗=17∗» — B (какие суммы возможны).
  Факт-чекер проверяет класс у каждой задачи на построение, для B — что
  переформулированный вопрос не выдаёт ответ сам по себе;
- **усиленный вопрос** (решение владельца 2026-09-30, T9c, hundred-from-threes):
  источник просит пример («улучшите результат», «приведите пример»), а канон
  спрашивает экстремум («наименьшее число троек»). Условие дословно, вопрос
  усилен только в строке формата; в `sourceHint` — «· дословно, вопрос усилен ·»;
  эталон — полный перебор (официальный пример подтверждает только оценку
  сверху); задача — в страте риска; пометка в proofs §0 / §0.1 и в §8 отчёта
  «канон усилен относительно источника»;
- **сужение прочтения** (T8d, five-sums): источник говорит «только три значения»
  (парные суммы лежат в множестве), а без дополнительной оговорки решений несколько.
  Условие дословно; в **строке формата** добавляют ограничение («встречаются все три
  значения»), которого нет в теле источника. Это не «усиление вопроса» (вопрос тот же:
  «какие числа»). В `sourceHint` — «· дословно, прочтение сужено строкой формата ·»;
  в `T*_SRC[slug].note` — явно, что без сужения наборов больше; эталон — перебор при
  суженном прочтении; задача в страте, если офиц. файла нет. «Ровно три» в теле
  условия писать нельзя (подмена текста источника);
- **авторский канон** (пометка «original olympiad-style», нет источника):
  сверять с источником нечего. Если в пакете канон остаётся авторским —
  пометка «авторская, в аудите не проверяется» в §0 proofs и в шапке
  отчёта; эталон пересчитывается как у любой задачи, но в счёт «офиц.
  ответы N/N» задача не входит. Предпочтительно — **замена задачей по
  источнику** (решение владельца 2026-10-03, T9d): slug, место в списке и
  прогресс сохраняются ([E]), уровень — класс темы (олимпиада для 5–6 кл.
  считается 6-м), канон дословно + строка формата, старый канон и варианты —
  в proofs §2 (класс R), сдвиг содержания — в proofs §0.2 и §5 отчёта;
  факт-чекер проверяет, что в `sourceHint` не осталось «original»;
- **формула, придуманная в подсказке** (решение владельца 2026-10-03, T9f,
  «дракон» Ust 2006.6.7): если эталон канона получается только из модели,
  которой нет в условии (подсказка «предположи, что e = p · h + q»), а
  официального решения нет — задача считается авторской и идёт в класс **R**
  (замена задачей по источнику). Если у старой задачи нет попыток и наград,
  допустим **новый slug** со сбросом: бэкап БД → сид → удаление старой задачи
  разовым скриптом (dry run, затем `--apply`); в proofs §2 — старый канон и
  варианты со ссылкой на замену, в отчёте — число удалённых попыток (0);
- официальный ответ из источника совпадает с `acceptedAnswers[0]`;
- если официального решения нет — отметить «без внешнего источника,
  страта риска» и включить задачу в соответствующий блок §6;
- **решение из каталога, а не от организаторов** (T9e, 2026-10-03: МП 1994
  и 1997 — решений на сайте праздника нет, ответ — problems.ru): в счёт
  «офиц. ответы N/N» входит, но задача — в страте риска с пометкой «решение —
  каталог <где>, а не организаторы» (proofs §0 и отдельный подраздел §0,
  §6 и §8 отчёта); эталон подтверждается независимым пересчётом;
- **официальный ответ из примера** (T9e, V1 К2: МП 2001, mpr01): если строки
  «Ответ:» у организаторов нет или она пустая, а ответ — пример из
  официального решения, в proofs §0 и §0.1 писать явно: «отдельной строки
  «Ответ:» нет; ответ взят из примера … в официальном решении». В страту
  риска задача не идёт: решение организаторов есть;
- **артефакты старого сида** — фразы, которых нет ни в сборнике, ни у
  организаторов (фамилия автора сборника «(Ященко)», начало официального
  ответа в строке формата «например «0+12+…=96»»): проверять по **обоим**
  текстам, снимать, перечислять в отдельном подразделе proofs §0; тест —
  фраза не встречается ни в одной сущности пакета;
- **основа канона при двух текстах организаторов** (T9f): если у олимпиады
  есть и листок условий, и книжка «Задачи и решения», основа — книжка (для
  Устной — 2011 и позже), иначе листок; в proofs §0.1 — две колонки (сборник
  и организаторы) и столбец «Основа»; опечатки набора (латинская «M» в
  кириллическом слове) правятся, пометка — в §0.1;
- **колонка «текст организаторов» независима** — класс 1 §0. Сверка — только
  `origFile` + `origSha256` и чтение листка скриптом proofs (T8d и далее).
  Отдельная константа `O_*` с тем же литералом, что `T_*`, без файла и хеша —
  не сверка;
- **официальный ответ не из сида** — класс 3 §0. `official: null`, если в
  файле организаторов ответа нет;
- **класс A по вариантам ≠ B2** (T8c, V1): неверный эталон варианта — класс A,
  не B2. Пересечение писать явно: либо V + A + B2 без двойного счёта = числу
  сущностей, либо «A ⊂ бывш. B2» одной строкой;
- **опечатка источника** (T8c обжоры «есть»): не править; если сомнительно —
  спросить владельца;
- **сид vs источник** (T8b): если сид не из книги или текст расходится —
  класс **R** или решение владельца, не класс A;
- **SVG сверяется с PDF-источником** (T8b, 3.1): не «похоже на ∞», а
  отрисовано и совпадает по геометрии, стрелкам, пропорциям петель
  (политика A). Если в книге рисунка нет — SVG канона не рисуем «от себя»
  (T8e: муравьи, часы, колбы, тигры); вымышленная схема вводит в заблуждение.
  Число клеток верное, а блок повёрнут (3×4 вместо 4×3) — править ориентацию
  по PDF (T8e, третья рыбка);
- **неполный ответ организаторов vs наша замена.** Официальный ответ
  сохраняется как есть, если нет решения обосновать расширение (Пончик T8b:
  вторник математически допустим, в эталон канона не кладём). Наш ответ
  заменяет ответ организаторов — **только по решению владельца**;
- **решения организаторов:** порядок шагов — `project-context.mdc` / локальная опись
  и поиск выше (`risk`, `searchLog`; локально 1–2; шаг 3 — **Implementer сам**. **V2-files (Claude) в сеть без команды владельца не ходит; при необходимости сам задаёт владельцу вопрос в сессии (что открыть и зачем), а не откладывает в отчёт.**).
  Файл метода — в
  `tmp-<пакет>/` или URL, иначе это не сверка (T8b eight-lap до PDF 6 кл.);
- **grade по туру олимпиады** (T9f): уровень канона согласован с M6 — у
  Устной олимпиады третий тур → high, первый и второй → mid; смена grade —
  в proofs §0 и шапке отчёта; после смены `SIMILAR_HARDER = 0` (валидатор);
- у вариантов: они **не должны** ссылаться на канон, но могут ссылаться
  на тот же источник со своим номером;
- если наше решение расходится с официальным — обосновать, почему наше верно.
**Формат артефакта:** таблица «канон / источник / ссылка / офиц. ответ /
наш ответ / совпало?».
**Чего НЕ делает:** не считает числа, не проверяет формулировки, не
оценивает математическую логику.

### Группа CODE — аудит кода
Роли этой группы активируются, когда меняется код (`lib/**`, `app/**/*.ts`,
`scripts/**`), а не только контент.

#### [D] Код-ревьюер — TS-код решателей, проверок, тестов
**Что проверяет:**
- `t*-solvers.ts`: корректность функций, JSDoc с обоснованием границ
  перебора;
- `t*-checks.ts`: соответствие решателя и выкладки, отсутствие дублирующих
  вызовов, отсутствие захардкоженных значений (если параметр может
  меняться — должен быть параметром);
- `t*-audit.test.ts`: соответствие `it.each` числу проверок; наличие
  страховочных тестов (дословность, вырожденные варианты, выкладки без
  дробей); **структурный тест** на `official` / `orig` (§0: `officialFile`,
  `origFile`, sha256); **поля `risk` и `searchLog`** (enum; нет поля /
  значение вне enum — падение; при `risk !== linear`: шаги 1–2 в журнале;
  шаг 3 — **Implementer сам, без команды**. **V2-files (Claude) в сеть без команды владельца не ходит; при необходимости сам задаёт владельцу вопрос в сессии (что открыть и зачем), а не откладывает в отчёт.**
  При `official === null` и `risk !== "linear"` в `searchLog` обязана быть
  строка шага 3 (`url` начинается с `http`); иначе тест падает. Статус
  `"не искалось"` при `risk !== linear` — падение. Статус
  «не проверялась — линейный канон» при нелинейном `risk` — падение);
- `scripts/audit-t*-proofs.ts`: детерминизм, отсутствие `Date` / `random` /
  `uid`; скрипт **читает файл** `tmp-olymp6/txt/<origFile>` (не копию из
  `t*-checks.ts`) и падает при расхождении хеша / текста; печатает
  `searchLog` в proofs §0;
- типы: `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` — не
  нарушены ли;
- ошибки `tsc`: только предсуществующие на базе, не регрессии пакета;
- выборка строк для Verifier-а (§6 отчёта) — равномерная: по одной строке
  на задачу с чередованием канон → i1 → i2, а не «каждая k-я» (при k = 3
  «каждая 3-я» даёт только i2).
**Формат артефакта:** список проверенных файлов + конкретные замечания;
с числами — «проверено N функций, у K нет обоснования границ», а не
только перечень типов границ.
Если код не менялся — писать «код не менялся», но проверить хотя бы границы
перебора в JSDoc.

#### [E] Архитектор — контракты данных, схемы, миграции
**Что проверяет:**
- `TaskSeed` / `TaskInstanceSeed`: все ли поля консистентны (`title`,
  `sourceHint`, `acceptedAnswers`, `hints`, `relatedDocSlugs`);
- валидаторы: `INSTANCE_ANSWER_MONOTONE`, `INSTANCE_TITLE_MISMATCH`,
  `INSTANCE_HINT_DOC_UNRELATED` — 0 ошибок? Если предупреждения —
  обоснованы?;
- `sourceHint` для олимпиадных канонов: есть ли «· дословно ·» и
  «офиц. решение: …»;
- флаг `all` (если есть — совпадает ли множество ответов решателя целиком
  с `acceptedAnswers`);
- `acceptedAnswers`: все ли формы записи (число, строка, список, «или»-формы)
  согласованы; в `acceptedAnswers` типа `text` нет многоточий «…» / «...»
  и других сокращений (ответ-список — полностью), иначе полный ввод ученика
  не совпадёт при точном сравнении;
- ответы-списки переменной длины (первый случай — T4c3, 2.7.3: «12, 13» /
  «10, 11» / «7, 8, 9»): строка формата не называет число элементов
  («оба варианта», «два числа») — иначе она выдаёт ответ и ломается на
  варианте другой длины; порядок элементов задан строкой формата («по
  возрастанию»); у каждой сущности обе формы — «a, b» и «a,b» (нормализатор
  пробел после запятой не сворачивает); отрицательный контроль включает
  неполный список (подмножество правильного);
- ведущие нули: нормализатор (`lib/trainer/answer.ts`) их не сворачивает,
  поэтому у ответов-дат и чисел с нулём впереди в `acceptedAnswers` есть
  все формы («04.01.2030», «4.01.2030», «4.1.2030», «04.1.2030»);
- ответ кодирует направление («как изменится …» — «увеличится на 6» /
  «уменьшится на 28»): числовые формы в `acceptedAnswers` — только со знаком
  («+6», «-28», «−28»); голое число без знака не принимается (у одних
  сущностей оно означало бы рост, у других — убыль), и оно же — в
  отрицательном контроле (T9a, rect-wh-change i2, находка V2);
- связи между файлами сида (вариант в `extra-instances`, канон — в основном
  файле: слаги совпадают?);
- миграции и схема БД — если пакет меняет структуру;
- прогресс учеников: при правке эталона (класс A) или при **V** (возврат
  к дословному тексту **той же позиции** источника с **тем же ответом**)
  записи `Attempt`, `TaskXpAward` и кубки **не пересчитываются** —
  ученик отвечал на тот текст, который видел, запись прогресса — исторический
  факт. Новые попытки проверяются по новому эталону. Если позиция или ответ
  не те же — это **R**, не V (прогресс сбрасывается, §13). В §8 отчёта — одна
  строка со ссылкой на это правило, без обсуждения в каждом пакете
  (правило зафиксировано 2026-09-28 после T4c1, de facto действовало с T4a);
- **V2 до мержа** (T9f, 2026-10-07; T1f ниты, 2026-10-11): слой **V2-files**
  идёт **до** каждого PR и мержа в `main`, **включая правки нитов** (новый
  код). Прецедент: `5215875` смержен без повторного V2 и вернул B3 в #53 i2.
  Находки V2 закрываются в том же PR пакета. Если V2 пришёл после мержа —
  отдельная ветка фикс-пакета. V1-text пакет не закрывает;
- **после замены источника — трекер** (T8b, §3.1.5-eight): прежние
  `duplicate_of` / `alias_of` инвертируются или удаляются; нельзя оставлять
  двухстрочное `duplicate_of` без цели. После R-удаления — `skip`;
- **B3-счёт при R** (T8b / T9f): раздельно — «B3 живых задач = N; R-замена =
  1 канон + 2 варианта»; удалённые сущности не входят в порог 15;
- **Attempt: единицы счёта** (T8c): «X задач × 3 сущности = 3X проверок»,
  не «X слагов × i0/i1/i2»;
- **эталон канона по решению владельца** (T8b, Пончик): прогресс не
  пересчитывается (то же правило, что у класса A). При замене вариантов —
  выгрузить число `Attempt` для информации;
- **трекер и `officialFile`:** перед записью `officialFile` /
  `officialSha256` в `coverage-m6.json` — **проверить схему**
  (`lib/content/coverage-m6.ts`). Если полей нет — **не добавлять**; URL
  источника — в `notes`. Не ломать тест трекера;
**Формат артефакта:** список изменённых/добавленных полей и их валидация.

## 2. Что НЕ входит в playbook

- **[B-математик]** — отдельная роль «Математик» (проверка доказательств,
  границ перебора, единственности ответа) **не активна по умолчанию**. По
  опыту серии T9→T3b, Implementer и так считает математику, а ревьюер ловит
  остатки. Активируется только по запросу пользователя.
- Специфические роли под единичные задачи — не плодим, пока не понадобится.

## 3. Правила активации (по типу изменений)

LLM смотрит на `git diff --name-only` относительно базы и по таблице
выбирает роли:

| Изменённые пути | Обязательные роли | Опционально |
|---|---|---|
| только `content/seed/**` | [A] [B] [C] | — |
| `content/seed/**` + `lib/content/audit/**` | [A] [B] [C] + [D] | [E] |
| `lib/content/audit/**` (без seed) | [D] | [E] |
| `content/seed/**` + схема БД / миграции | [A] [B] [C] + [E] | — |
| `app/**/*.tsx`, `components/**` | [F] [G] + [D] | — |
| `scripts/**` (пайплайн LLM) | [H] [I] | — |
| смешанный случай | объединение обязательных ролей | — |

**Правило обязательности:** если для типа изменений роль в колонке
«Обязательные» — LLM **не может** её пропустить. Если пропускает — обязана
явно написать причину в шапке (§4).

**Правило эскалации:** если Verifier (DeepSeek) нашёл дефект, который не
покрыт ни одной активной ролью, пользователь добавляет роль из §1 в
обязательные для этого типа изменений **навсегда** (запись в §3).

## 4. Формат отчёта (шапка)

В начале `docs/REVIEW-AUDIT-<тема>.md` добавить блок:

```
> ## Самопроверка Implementer-а
> **Активные роли:** [A] [B] [C]
> **Причина:** изменения только в `content/seed/*.ts` (см. §3 playbook).
> **Пропущенные роли:** нет.
> **Краткий итог:** [A] нашёл 2 опечатки (исправлены), [B] нашёл 3
>   формулировки (исправлены), [C] проверил 15 источников, 13 совпало,
>   2 без внешнего источника — страта риска.
```

Если пользователь принудительно активировал роль — добавить:
```
> **Принудительно активировано пользователем:** [D] Код-ревьюер
>   (комментарий: «проверь JSDoc у новых функций»)
```

Если роль пропущена с обоснованием:
```
> **Пропущено:** [D] — код не менялся (`git diff` подтверждает)
```

### Комплект передачи Verifier-у

Отчёт **без proofs не передаётся**: без доказательств V1 неполный, и
Verifier вправе вернуть пакет, не начиная проверку. Комплект — три файла:

1. `docs/ai-workflow/PROMPT-VERIFIER.md` — промпт Verifier-а (в git);
2. `docs/REVIEW-AUDIT-<тема>.md` — отчёт (локальный);
3. `docs/audit/<тема>-proofs.md` — доказательства, **сгенерированные на том
   же SHA**, что указан в шапке отчёта (регенерация скриптом
   `scripts/audit-<тема>-proofs.ts` перед передачей).

В шапке отчёта — строка:
```
> **Комплект для Verifier:** PROMPT-VERIFIER.md + этот отчёт +
>   docs/audit/<тема>-proofs.md · SHA `<sha>`
```
Без `· SHA <sha>` строка комплекта не засчитывается (T1g).

**Комплект для Verifier-1 (V1-text).** Три файла как текст (без корня
репо): `PROMPT-VERIFIER.md` + отчёт + proofs. Вердикт только
`V1-text-passed` / `V1-text-failed`. Без раздела «что не проверял —
задача V2» V1 не закрыт.

**Комплект для Verifier-2 (V2-files, обязателен до мержа).** Промпт
`docs/ai-workflow/PROMPT-VERIFIER-2.md` + отчёт + proofs + **открытый корень проекта**
(сиды, `lib/content/audit/**`, трекер). Если V1 уже прошёл — §9 отчёта
и список «не проверял — задача V2». Цель V2 — файловый слой, не повтор
арифметики V1. Пакеты ≤ 100 сущностей. Вердикт `V2-passed` /
`V2-failed с блокерами`. Слои — §11.

## 5. Формат отчёта (§10 — таблица самопроверки)

В §10, **перед** таблицей закрытия замечаний, добавить:

```
### Самопроверка по ролям

| Роль | Что проверил (артефакт) | Нашёл | Исправлено |
|------|------------------------|-------|------------|
| [A] | пересчитал все суммы: §2, §3, §7.2, §7.3, §10 | 2 опечатки | да |
| [B] | поиск «В каноне» по всем 45 сущностям; прогон findVariantCollisions; проверка 13 названий | 3 | да |
| [C] | открыл 13 ссылок problems.ru / matholymp67; сравнил офиц. ответ | 0 расхождений, 2 без источника | — |
```

«открыл Z ссылок», «пересчитал W сумм»). Не «проверил».

Если роль ничего не нашла — писать «чисто», не оставлять пустой.

## 6. Формат префиксов в таблицах замечаний

В §5, §6, §8, §10 — замечание начинается с префикса роли:


## 7. Контроль со стороны пользователя

Пользователь имеет право:
- **Требовать активации роли** — «добавь [D]», «проверь ещё [C] для этого
  пакета».
- **Требовать деактивации** — «не нужно [C], все источники я проверил сам».
- **Требовать обоснования** — «почему [D] не активирован при изменениях в
  `lib/content/audit/`?».
- **Отменять §3** — «в этом пакете исключение: активируй [A] [B] [D] без [C]».

LLM обязана:
- указывать активные роли в шапке;
- указывать причину выбора (по §3);
- при пропуске — обоснование;
- при переопределении пользователем — фиксировать в шапке.

## 8. Правило «не сжульничать»

**Обязательный артефакт для каждой роли.** В таблице самопроверки (§5)
колонка «Что проверил» должна содержать:
- **число проверенных единиц** («45 сущностей», «13 ссылок», «все суммы в
  §2, §3, §7»);
- **что именно проверялось** («поиск подстроки X», «открыл URL Y»,
  «пересчитал `C(n,k)` для n = 1..10»);
- для роли [A] — **номера** проверенных сумм и строк (разделы + номера строк
  proofs), а не только их количество;
- для роли [D] — **числа**: сколько функций / файлов проверено и у скольких
  найден дефект («14 функций, у 0 нет обоснования границ»).

Фразы типа «проверил всё», «чисто», «замечаний нет» без артефакта —
**считаются недостаточными**. Пользователь или Verifier может потребовать
расшифровку.

## 9. Расширение playbook

Новые роли добавляются в §1 с указанием:
- буква роли (по порядку внутри группы);
- что смотрит;
- что НЕ входит в эту роль;
- когда активируется (для §3).

Правило: **не больше одной роли за раз**. Если за пакет добавили две новые
роли — это уже перегруз. Лучше применить одну, посмотреть эффект, потом
следующую.

## 10. Что playbook НЕ заменяет

- **V1-text (DeepSeek)** — не отменяется. Роли самопроверки — предварительная
  фильтрация, не финальная проверка и не замена V2.
- **V2-files** — отдельный слой (§11); playbook его не заменяет.
- **Общие слепые пятна Grok + DeepSeek в тексте** закрывает V2-files
  (прецедент T8: SVG, сид, трекер).

## 11. Слои верификации

- **V1-text (DeepSeek)** — численник, cross-ref, формулировки, дословность
  по тексту. Нет доступа к файлам. Вердикт: `V1-text-passed` /
  `V1-text-failed`. Промпт: `docs/ai-workflow/PROMPT-VERIFIER.md`.
- **V2-files (Claude Code)** — сид, SVG, решатели, трекер, БД, истинность
  подсказок, независимость вариантов. Обязателен до мержа. Вердикт:
  `V2-passed` / `V2-failed с блокерами`. Промпт: `docs/ai-workflow/PROMPT-VERIFIER-2.md`.
  **V2-files запускается только в Plan Mode.** Пользователь открывает
  Claude Code с корнем проекта, нажимает `Shift+Tab` (индикатор «Plan»),
  передаёт задачу. Если в сессии появляется изменение файлов, git-операция
  кроме read-only (`git status`, `git log`, `git diff`) или создание любых
  файлов — сессия недействительна, изменения откатываются, V2 запускается
  заново.
- **Порядок:** Implementer → V1-text → правки → V2-files → правки →
  commit → PR → merge.
- **Правило:** V1 не заменяет V2 и не имеет права закрыть пакет. V2 не
  повторяет работу V1 в текстовом слое. Если V2 нашёл блокеры — закрытие
  и короткий повтор V2 до мержа.

Прецедент T8a/T8b (2026-10-07): V1 без файлов пропустил блокеры
восьмёрки, Пончика-вариантов и крокодилов i1; V2 с корнем проекта их
поймал.

### Official [C]
Три **верхнеуровневых** статуса `official` — про **способ доступа к ответу**,
не про первоисточник и не про topic-gate. Счёт «офиц. ответы N/N» — по этим
трём. Не смешивать:
- **листок** — ответ напечатан рядом с условием в листке организаторов;
- **вторичный сборник / файл решений** — ответ найден в файле сборника или
  решений (способ A или C), не в листке. Подтипы внутри этого статуса:
  **сводник** и **файл решений**; в отчёте подтип можно указать явно
  (например «файл решений»), но верхний статус остаётся один.
  В таблице proofs §0 писать подтип полностью («файл решений»), не
  сокращение «файл» (T1g);
- **страта** — ответа нет ни локально, ни после шага 3 в сети;
  `official = null`. В `searchLog` обязана быть строка шага 3
  (`url` с `http…`) с итогом `"найден, не скачан (обрыв)"` или
  `"нет на сайте организаторов (HTTP 404)"`. Статус `"не искалось"`
  запрещён. Шаг 3 — **Implementer сам, без команды**. **V2-files (Claude) в сеть без команды владельца не ходит; при необходимости сам задаёт владельцу вопрос в сессии (что открыть и зачем), а не откладывает в отчёт.**

Порядок поиска ответа: (1) листок; (2) файл решений (`решения математика/**`,
zip); (3) только условия → страта.

**Классификация источников [C].** Источник задачи — первоисточник с
атрибуцией (по умолчанию олимпиада). Способ доступа (A–E по реестру
`CONTENT-QUALITY.md` §2) записывается отдельно. 6math — агрегатор олимпиадных задач (вместе с matholymp67), не отдельный
класс. Первоисточник 6math-канонов — **олимпиада, из которой задача взята**
(указана рядом с задачей в 6math); 6math — способ доступа A, не первоисточник.
В таблице AC и в §5 отчёта — название олимпиады, не «олимпиада из книги».
Позиция в 6math — указатель для topic-gate и трекера. Три статуса `official` — про способ
доступа к ответу.

`officialSource: listok` — поле `T*_SRC`, не колонка `TaskSeed`; определять
в глоссарии отчёта, не только в proofs.

### H [H]
Готовое уравнение в подсказке — класс H, **верно оно или нет — не имеет
значения**. Если подсказка содержит алгебраическую формулу, описывающую
ответ, — это H. Прецедент T8o наклейки, `915c797`: уравнение
`7 + 7(x−7) = 11 + 11(x−11)` верно (x = 17, набор 77); дефект — H.

### Формы эталона [B]
У каждого канона явно: число без единицы и с единицей; словесная форма;
дробь («1/4», «0,25»); дата («19 февраля», «19.02»); имя в падежах
(«Вася» / «у Васи» — минимум именительный и один падеж из условия;
либо явная пометка «только именительный — решение владельца»; T1g
велопробег: «антон» / «у антона»); список «или» / запятая. Если месяц из
{28, 29, 30, 31} не единственен — только число без месяца (T8o баран i1:
в `ae54252` формы «15» / «15-е» / «15 числа» / «15-го»; в `915c797` было

явно (T8l `bus-stops` — проверить по файлу). Пример в строке формата
**не** совпадает с эталоном (T8o баран: не «19 февраля»).

### Классы [B]
V, A, B2, B3, H, R. Класс B (CONTENT-QUALITY §4): условие дословно, вопрос
переформулирован под число / да-нет / список. Это не B2 (числа изменены)

тема потребует. Три разных ответа в семействе; ответ варианта не совпадает

**R (замена)** — канон был `original · olympiad-mentor …`, либо дословный
текст **не совпадает с той же позицией источника или меняет ответ**.

**V (возврат к дословному)** — канон был переформулировкой или близким

с **тем же ответом**. V только при той же позиции и том же ответе.
Прогресс **не сбрасывается** (правило T4c1).
